# Testes e qualidade — site Reset IA

O site tem um objetivo: levar ao RESET AI Score e, dali, à conversa no WhatsApp. A pirâmide abaixo protege isso do mais barato ao mais caro. Tudo roda no CI (`.github/workflows/ci.yml`).

## Evolução do AI Score: o que os testes novos garantem

Medido em 01/11/2026, na branch `feat/ai-score-evolucao`: unidade **282** (21 arquivos), banco **184** asserções, função **37** testes, E2E **294** execuções nos dois projetos (286 passando, 8 puladas de propósito), lint, tipos (`next typegen && tsc -p tsconfig.test.json`) e knip limpos.

| Risco                                    | Onde                                                           | O que o teste prova                                                                                                                                                                                                                                                                   |
| ---------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## O que ainda não foi medido

- **Baselines visuais** (`npm run e2e:baselines`, Docker): ver `docs/ai-score-evolucao.md`. As telas mudaram nas fases 4 a 6 e os prints Linux precisam ser regenerados antes do CI visual voltar a ser confiável.
- **Leitor de tela de verdade** (VoiceOver, NVDA): o axe não substitui. O que foi conferido é por regra automática, não por escuta.
- **Gmail e Outlook**: o e-mail do relatório não foi aberto num cliente real.
- **Produção**: nada disto roda contra o ambiente publicado; o smoke de produção acontece depois do deploy (`docs/deploy.md`, passo 6).

## Rodando localmente

```bash
npm run test              # unidade
npm run build && npm run e2e   # E2E (sobe o servidor sozinho)
npm run e2e -- --project=desktop-chromium tests/e2e/cta-whatsapp.spec.ts
npx lhci collect && npx lhci assert   # Lighthouse sem publicar o relatório (precisa do out/)
npm run check:html && npm run check:size && npm run check:rotas && npm run check:falta && npm run check:links
npm run test:banco        # migração do Supabase num Postgres temporário (precisa de initdb/pg_ctl/psql)
npm run e2e:baselines     # gera baselines visuais na imagem Docker do Playwright (Linux); rodar depois do build
```

## Regressão visual sem flakiness

Snapshots só nos projetos `reduced-motion*` (sem transição nem scroll suave). Fontes e imagens aguardadas antes do print. Baselines são de Linux (a mesma imagem do CI); em macOS o teste é pulado. Para atualizar depois de uma mudança visual intencional: workflow "Atualizar snapshots visuais" ou `npm run build && npm run e2e:baselines`.

## O que fica de fora (de propósito)

- Testes de snapshot de componentes React: a regressão visual real cobre melhor e não quebra com refatoração.
- Storybook: site pequeno; os componentes vivem no contexto das seções.
- Cobertura mínima como portão: o site é conteúdo; os números que importam estão no Lighthouse e no axe.

## Exclusões do axe

As órbitas do hero (`data-decorativo`, `aria-hidden`) ficam fora do axe: repetem as três áreas, que aparecem como texto na seção Áreas.

## Supabase nos testes

O CI builda com `NEXT_PUBLIC_SUPABASE_URL=https://supabase.invalid`: o site se comporta como em produção e os specs interceptam `**/rest/v1/**`, `**/auth/v1/token**` e `**/functions/v1/**` com `page.route`, conferindo o que é gravado (a avaliação sem dados pessoais, o lead ligado a ela) e simulando o login do admin. Sem as envs (build local comum), os mesmos specs rodam em modo demonstração. Nenhum teste toca um banco de verdade, nem o smoke contra produção.
